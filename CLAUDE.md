## Project

**Movva** is a weekly schedule for competitive sport plus strength training, at movva.eu. You set your sport, your training and match days and your exercises; Movva places the strength sessions around the sport, keeps your log and tells you what to lift today.

No account and no server: the log lives in the browser and a plan is shared through a link. The code is laid out so a server (accounts, sync) can be added later without a rewrite.

Movva grows in numbered modules, each specified in [docs/modules/](docs/modules/). UI copy is Dutch first; English follows in its own module. Code, comments and this file are English. Commit messages are Dutch: `Module N: <stap>`.

## Way of working

1. A module starts as a short spec in `docs/modules/NN-name.md`: why, scope decisions, acceptance criteria. Kay approves the spec; that is the one stop before code.
2. The module is built in one go. Rules are written test-first in `src/lib`.
3. Review is on the result, not on diffs: a pull request with a summary, green CI, and a preview to try on a phone.
4. Merging to `main` publishes to movva.eu (once hosting is connected).

A presentation change is verified on a really rendered page at 390 px wide, light and dark, not with a claim that it will look fine.

## Stack

SvelteKit 3 (Svelte 5 runes) · TypeScript strict · Zod 4 · Vitest · `@sveltejs/adapter-static`.

SvelteKit 3 came out in October 2026, after most model training data. Look APIs up with the Svelte MCP server (`.mcp.json`) or `npx @sveltejs/mcp` instead of writing them from memory. Notable: config lives in `vite.config.ts` (there is no `svelte.config.js`), `$lib` is now `#lib`, and the service worker uses `$app/env`, `$app/paths` and `$app/manifest`.

## Architecture

- **`src/lib/`** is plain TypeScript without DOM or storage: `dates`, `plan/schema` (+ `plan/default-plan`), `log/schema`, `phase`, `advice`, `plates`, `planner`. Every file has a `.test.ts` next to it. Screens call these functions and contain no rules of their own.
- **`src/routes/`** holds the screens. `+layout.ts` prerenders everything into static files; a page that depends on today's date or on browser storage sets `ssr = false`.
- **Imports** use `#lib/…` with an explicit `.ts` extension. `#lib` resolves through Node subpath imports, which need exact paths. Relative imports inside `src/lib` carry `.ts` too.

## Settled decisions (do not reopen without a reason)

- **Dates** are `'YYYY-MM-DD'` strings and all date arithmetic runs on `Date.UTC`, so a 23- or 25-hour day can't shift a week number. Tests run with `TZ=Europe/Amsterdam` so the clock changes really happen in them.
- **The plan is data**, checked by Zod on every way in: a link, an import, storage. Ids are slugs because they end up in links, keys and HTML attributes.
- **Weekly rules are data**: each slot lists its allowed days in order of preference, and may be `optional` (a choice per week), `notBeforeMatch` or `onlyWithoutSport`. `planWeek()` applies them and reports why something was dropped. The handball table from Kay's plan is a test.
- **A logged entry describes itself**: exercise names and the week, block and light-week flag at the time. Ids are `${date}_${ref}`, so saving again overwrites and a future sync can merge on id plus `updated`.
- **`advice()` returns reasons, not sentences.** The screen phrases them, so a second language needs no logic changes.
- **Weights are kilograms.** (movva-app stored pounds; Movva is European.)
- **Plates**: the fewest plates, counted in grams. "Heaviest plate first" fails for custom plate sets such as only 15s and 10s.
- **Zod's readable API stays**, although `zod/mini` would save about 20 kB gzip. Revisit only if bundle size starts to matter.
- **Text is rendered with `{…}`**, which escapes it. `{@html}` is never used on anything that can come from a plan or a log.
- **Fonts are bundled with the app**, never loaded from Google Fonts, which would hand every visitor's IP address to Google.

## Gotchas

- `noUncheckedIndexedAccess` is on: `array[i]` is `T | undefined`.
- Vitest runs with `requireAssertions`: a test without an `expect` fails.
- `npm install` on npm 10 can crash with `Cannot read properties of null (reading 'edgesOut')` on the Vitest 4 tree; that is why Vitest is on 5.
